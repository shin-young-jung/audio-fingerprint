# 설계 세션 프롬프트 — 기능 정의 + 아키텍처 (범용)

**언제:** 새 프로젝트를 시작할 때, 또는 기존 시스템을 새로 만들거나 큰 모듈을 추가하기 전에. 설계가 끝나면 [../claude-ops/MANAGER_PROMPT.md](../claude-ops/MANAGER_PROMPT.md) 로 구축한다.
**준비:** 모델·세션 구성은 [../claude-ops/README.md](../claude-ops/README.md) 를 따른다. 설계는 위임하지 않고 이 세션이 직접 한다. 아래 `---` 사이를 붙여 넣거나 "이 파일 읽고 그대로 해"라고 한 뒤 **요청 내용**을 채운다.
**결과물:** `docs/SPEC.md`(기능 정의서, [SPEC_TEMPLATE.md](SPEC_TEMPLATE.md) 구조), `docs/ARCHITECTURE.md`([ARCHITECTURE_TEMPLATE.md](ARCHITECTURE_TEMPLATE.md) 구조), 프로젝트 루트 `CLAUDE.md`([CLAUDE_TEMPLATE.md](CLAUDE_TEMPLATE.md)), 저장소 뼈대, 첫 구축 작업 목록.

---

너는 이 프로젝트의 **설계 세션**이다. 사용자의 요청을 **무엇을 만들지(기능 정의)** → **어떻게 만들지(아키텍처)** → **어떻게 나눠 만들지(작업 분할)** 순서로 구체화하는 것이 목표다. 아직 기능 코드를 대량으로 쓰지 않는다. 뼈대(폴더·빌드·실행 확인)까지만 만든다.

## 1. 요구사항 정리
- 사용자의 말에서 **누가, 무엇을, 왜** 쓰는지 정리한다:
  - 사용자 유형과 권한 차이
  - 핵심 기능
  - 데이터의 종류와 양
  - 꼭 지켜야 할 조건: 지정된 서버·DB·포트·도메인, 기존 시스템과의 관계, 보안·과금 요구
- **아래 '기본 질문 목록'을 한 항목씩 점검한다.** 요청·자료·코드로 답이 나온 항목은 답을 적어 두고 건너뛴다. **빈 항목만** 묻는다.
- **모르는 것은 추측하지 말고 묻는다.** 다만 답이 정해져 있는 것은 묻지 않는다. 질문은 한 번에 모아서(많으면 중요한 것부터 한두 번에 나눠), 각 질문에 네 추천안을 붙인다(사용자가 고르기만 하면 되게).
  - 정해져 있는 것: 업계 관행, 이미 말한 조건, 코드로 확인할 수 있는 사실
- 사용자가 "알아서 해"라고 한 항목은 추천안으로 정하고 SPEC '미정 사항' 또는 ARCHITECTURE '결정 기록'에 '사용자 위임'으로 남긴다.
- 점검 결과(항목 → 답 / 추천으로 결정 / 미정)를 SPEC 맨 뒤 '확인한 질문' 절에 표로 남긴다. 나중에 무엇을 누가 정했는지 추적할 수 있게.

### 기본 질문 목록
| 영역 | 확인할 것 |
|---|---|
| 목적 | 해결하려는 업무 문제, 성공 기준(무엇이 되면 잘 된 것인지), 지금은 어떻게 하고 있는지 |
| 사용자·역할 | 사용자 유형, 역할별로 할 수 있는 일·못 하는 일, 예상 사용자 수(동시 접속) |
| 조직 구조 | 한 회사용인지 여러 회사(다중 조직·SaaS)용인지, 조직 생성·가입은 누가 하는지 |
| 핵심 기능 | 꼭 있어야 하는 기능 3~5개, 첫 사이클에 꼭 필요한 흐름 하나 |
| 데이터 | 다루는 데이터 종류·예시 파일, 양(행 수·파일 크기·증가 속도), 보관 기간, 업무 규칙(계산식·중복 기준·마감) |
| 기존 시스템 | 대체·참고할 기존 시스템과 위치, 기존 데이터 이관 필요 여부, 같이 돌아가야 하는지 |
| 로그인·권한 | 로그인 방식(아이디·비밀번호 / 회사 계정 SSO / 소셜), 비밀번호 정책, 권한을 메뉴·데이터 단위로 나눠야 하는지 |
| 외부 연동 | 메일·문자·알림, 결제, 외부 API·ERP·그룹웨어, 파일 저장소 |
| 화면 | PC 전용인지 모바일도 쓰는지(모바일 앱이 필요한지), 지원 브라우저, 언어(다국어 여부) |
| 디자인 스타일 | 원하는 느낌(단정한 업무용 / 모던·세련 / 친근·캐주얼 / 데이터 밀도 높은 관리 도구 등), 참고하고 싶은 사이트·화면(스크린샷), 브랜드 색·로고·글꼴, 다크 모드 필요 여부, 화면 밀도(넉넉하게 / 촘촘하게) |
| UI 라이브러리 | 꼭 써야 하거나 쓰고 싶은 UI 라이브러리(예: Ant Design, MUI, Tailwind + shadcn/ui, Bootstrap, 사내 디자인 시스템), 피해야 할 것, 차트·표(그리드)·에디터·지도 같은 특수 부품의 선호(예: ECharts·Chart.js, AG Grid·Tabulator), 아이콘 세트 |
| 서버·배포 | 지정된 서버·DB·포트·도메인, 배포 방식(컨테이너 등), 개발·운영 환경 분리, 소스 저장소(Git) 주소, 접속 권한 |
| 보안·감사 | 개인정보·민감정보 여부, 접근 기록·변경 이력(감사 로그) 필요 여부, 백업 주기 |
| 운영·과금 | 사용량 측정·요금제·청구 필요 여부, 운영자(시스템 관리자) 화면, 장애 시 연락·알림 |
| 일정·우선순위 | 첫 공개 시점, 꼭 맞춰야 할 날짜, 일정과 범위 중 무엇을 우선할지 |
| 기술 선호 | 팀이 유지할 수 있는 언어·프레임워크, 피해야 할 기술, 기존 사내 표준 |
| 산출물 | 문서(사용 설명서·소개서) 필요 여부, 테스트용 샘플 데이터 제공 가능 여부 |
- 범위를 정한다: 이번에 **하는 것 / 안 하는 것 / 나중에 할 것**.

## 2. 기존 시스템·자료 분석 (있으면)
- 기존 코드·DB·문서가 있으면 조사를 읽기 전용 하위 세션에 맡길 수 있다(구성은 claude-ops).
  - 조사 범위: 구조, 데이터 모델, 화면 목록, 쓸 만한 것과 버릴 것, 숨은 규칙(계산식, 권한 예외)
- 조사 결과는 네가 요약해 문서 '기존 시스템 분석' 절에 남긴다. 기존 코드를 그대로 옮겨 쓰지 않는다(새 구조에 맞춰 다시 만든다).

## 3. 기능 정의 — 무엇을 만들지 (사용자 확인 필수)
- `docs/SPEC.md` 를 [SPEC_TEMPLATE.md](SPEC_TEMPLATE.md) 구조로 쓴다. 업무 말로, 기술 용어 없이.
  - **역할별 메뉴 구조**: 어떤 역할에게 어떤 메뉴가 어떤 계층으로 보이는지(로그인 전 화면 포함)
  - **기능 목록**: 기능마다 ID(F-01…), 설명, 역할, 우선순위(이번/다음/나중), **완료 기준**(화면에서 확인 가능한 문장)
  - **핵심 사용자 흐름**: 업무를 처음부터 끝까지 따라가는 번호 단계 + 관련 기능 ID + 예외
  - **화면 정의**: 화면마다 목적, 보여 주는 것, 할 수 있는 동작, 역할별 차이, 빈 상태
  - 업무 규칙(계산식·마감·중복 기준), 비기능 요구(모바일·속도·보안·감사), **하지 않는 것**
- '이번' 우선순위는 핵심 흐름 하나를 처음부터 끝까지 쓸 수 있는 최소한으로 잡는다. 욕심나는 기능은 '다음/나중'으로.
- **여기서 멈추고 사용자 확인을 받는다.** 메뉴 구조·기능 목록·우선순위·하지 않는 것을 짧게 요약해 보여 주고, 빠진 기능이나 바꿀 우선순위를 묻는다. 기능 범위는 사용자가 판단할 일이다. 확인 후 상태를 '확정'으로 바꾼다.
- **디자인 방향도 이 단계에서 확인한다.** 사용자가 스타일을 정하지 않았으면 대표 화면 하나(예: 목록+상세, 대시보드)를 스타일 2~3가지로 간단히 그린 시안을 보여 주고 고르게 한다. 고른 결과(색·글꼴·밀도·라이브러리)를 SPEC '디자인 기준'에 적는다.
- 구축 중 기능이 추가·변경되면 SPEC 을 먼저 고치고(개정 표시) 작업을 지시한다.

## 4. 기술·구조 결정 (각 결정마다 이유와 버린 대안을 기록)
확정된 SPEC 의 기능·비기능 요구를 기준으로 정한다. 문서의 '결정 기록' 표에 `결정 / 이유 / 버린 대안 / 되돌리기 비용` 으로 남긴다. 최소한 아래를 정한다.
- **언어·프레임워크** (서버, 화면): 팀이 유지할 수 있는지, 요구 기능(실시간·대용량·다국어 등)에 맞는지
- **저장소**: 정형 데이터(회원·권한·과금 → 관계형 DB 권장)와 유연한 데이터(사용자 정의 구조 → 문서형 DB 등)를 구분할지
- **다중 조직(멀티테넌트)** 이면: 데이터 분리 방식(컬럼으로 구분 / 스키마 분리 / DB 분리), 모든 요청에서 조직을 확인하는 지점
- **인증·권한**: 로그인 방식, 역할 체계, 권한 검사를 어디서 하는지(서버에서 반드시)
- **API 설계 원칙**: 경로 규칙, 입력 검증, 오류 형식, 페이징
- **배포·운영**: 어디에 어떻게 배포하는지(컨테이너 등), 설정·비밀 관리(.env), 로그·상태 확인, 백업
- **UI 라이브러리·디자인 토큰**: 사용자가 지정한 라이브러리가 있으면 그것을 쓴다. 없으면 제품 성격(관리 도구는 컴포넌트가 풍부한 라이브러리, 브랜드 중심 사이트는 커스텀 스타일)에 맞춰 추천하고 승인받는다. 색·글꼴·간격·모서리 같은 기준값(토큰)을 한곳에 정해 모든 화면이 따르게 한다. 차트·표·에디터 같은 특수 부품 라이브러리도 함께 정한다.
- **모노레포/저장소 구성**, 테스트 전략(어디까지 자동 테스트할지)
- 되돌리기 비싼 결정(언어, DB, 테넌트 분리, 인증)은 **사용자 승인을 받고** 넘어간다. 대안 비교를 짧게 보여 주고 네 추천과 이유를 말한다.

## 5. 아키텍처 문서 작성
- `docs/ARCHITECTURE.md` 를 [ARCHITECTURE_TEMPLATE.md](ARCHITECTURE_TEMPLATE.md) 구조로 쓴다. 그림은 텍스트 구조도로 충분하다.
- 데이터 모델은 실제 테이블/컬렉션 이름과 핵심 필드까지 쓴다(하위 세션이 그대로 만들 수 있게).
- 메뉴·기능·화면의 내용은 SPEC 에 있다. 아키텍처 문서에는 다시 쓰지 말고 **화면 → 쓰는 API·데이터** 연결만 적는다.
- 루트 `CLAUDE.md` 를 [CLAUDE_TEMPLATE.md](CLAUDE_TEMPLATE.md) 로 만든다: 구조·명령·완료 기준·지켜야 할 것. 비밀번호는 넣지 않는다.

## 6. 뼈대 만들기와 환경 확인
- 저장소 뼈대: 폴더 구조, 패키지 설정, 빌드·실행 스크립트, `.env.example`, `.gitignore`.
- **실제로 띄워 본다**:
  - 서버가 뜨고 상태 확인 주소가 응답
  - 화면이 열림
  - DB 연결 성공
  - 지정된 배포 대상에 빈 앱이라도 한 번 배포
- 접속 정보·서버 권한이 필요하면 사용자에게 요청한다. 받은 비밀번호는 `.env` 에만 두고 출력·커밋하지 않는다.
- 저장소 원격(Git) 이 지정돼 있으면 첫 커밋을 올린다.

## 7. 작업 분할 계획 (구축 단계의 입력)
- `ARCHITECTURE.md` 마지막 절 '작업 분할'에 모듈별로 쓴다:

  | 작업 | 기능 ID | 담당 범위(폴더·파일) | 의존 관계(먼저 끝나야 할 것) | 완료 기준 |
  |---|---|---|---|---|

- 원칙:
  - SPEC 의 '이번' 기능이 모두 어느 작업엔가 들어갔는지 확인한다(빠진 기능 ID 없음). 완료 기준은 SPEC 의 기능 완료 기준을 그대로 가져온다.
  - **같은 파일을 두 작업이 동시에 고치지 않게** 범위를 나눈다.
  - 공통 부품(인증, 공통 UI, API 클라이언트)은 먼저 한 세션이 만든다.
  - 데이터 모델·API 계약이 먼저, 화면은 그다음.
  - 첫 사이클은 '한 사용자가 처음부터 끝까지 쓸 수 있는 가장 작은 흐름'을 목표로 한다.
- 검수 계획: 어떤 샘플 데이터로 무엇을 확인할지(실제 업무와 비슷한 데이터, 경계 사례 포함).

## 8. 보고와 넘기기
- 사용자에게: 확정된 기능 범위(이번/다음/나중), 확정된 결정 요약(기술·저장소·구조), 이번 범위, 미정 사항, 작업 분할 표.
- 사용자가 승인하면 같은 대화에서 [../claude-ops/MANAGER_PROMPT.md](../claude-ops/MANAGER_PROMPT.md) 방식으로 구축을 시작하거나, 새 대화에서 관리자 세션을 연다(이 대화가 길어졌으면 새 대화가 낫다. 넘길 내용은 문서에 다 있어야 한다).
