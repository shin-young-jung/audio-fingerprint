# 기능 정의서 뼈대 (범용)

새 프로젝트의 `docs/SPEC.md` 를 만들 때 복사해 `< >` 를 채운다. '무엇을 만들까'를 정하는 문서이고, '어떻게 만들까'는 `docs/ARCHITECTURE.md` 가 맡는다.
읽는 사람은 사용자(범위 확인·승인)와 개발 세션(무엇이 되면 끝인지)이다. 기술 용어 대신 업무 말로 쓴다.
해당 없는 절은 지우지 말고 "해당 없음 — 이유"로 남긴다.

````markdown
# <제품명> 기능 정의서

작성 <날짜> · 상태 <초안 | 사용자 확인 | 확정 | 개정 n>

## 1. 한 줄 요약과 목표
- 한 줄 요약: <누가 무엇을 하게 해 주는 제품인지>
- 목표(성공했다고 볼 기준): <예: 엑셀로 하던 월말 보고 작업을 화면에서 끝낼 수 있다>

## 2. 사용자와 역할
| 역할 | 누구 | 하는 일 | 못 하는 일 |
|---|---|---|---|

## 3. 메뉴 구조 (역할별)
```
<역할 A>
├─ <메뉴>
│  ├─ <하위 메뉴>
│  └─ <하위 메뉴>
└─ <메뉴>
<역할 B>
└─ ...
```
- 로그인 전 화면(로그인·가입·안내)도 적는다.
- 사용자가 메뉴를 직접 만드는 제품이면 '기본 제공 메뉴'와 '사용자 정의 영역'을 구분한다.

## 4. 기능 목록
| ID | 기능 | 설명 | 역할 | 우선순위 | 완료 기준 |
|---|---|---|---|---|---|
| F-01 | <> | <한두 줄> | <> | 이번 | <무엇이 되면 끝인지, 확인 가능한 문장> |

- 우선순위: **이번**(첫 사이클) / **다음** / **나중**. '이번'은 핵심 흐름을 처음부터 끝까지 쓸 수 있는 최소한으로.
- 완료 기준은 화면에서 확인할 수 있게 쓴다(예: "조회자는 허용되지 않은 메뉴의 주소를 직접 열어도 볼 수 없다").
- 기능이 많으면 영역별로 나눈다(F-1x 데이터, F-2x 보고서 …).

## 5. 핵심 사용자 흐름
흐름마다 번호 단계로, 관련 기능 ID 를 붙인다.
1. **<흐름 이름>** (<역할>)
   1. <단계> (F-01)
   2. <단계> (F-02)
   - 예외: <중간에 실패하거나 권한이 없을 때>

- 꼭 지켜야 할 업무 규칙(계산식, 마감·승인 절차, 중복 기준, 보관 기간)
````
