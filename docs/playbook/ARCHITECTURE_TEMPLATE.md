# 아키텍처 문서 뼈대 (범용)

새 프로젝트의 `docs/ARCHITECTURE.md` 를 만들 때 복사해 `< >` 를 채운다. **무엇을 만들지(메뉴·기능·화면)는 `docs/SPEC.md`([SPEC_TEMPLATE.md](SPEC_TEMPLATE.md))에 먼저 확정**하고, 이 문서는 어떻게 만들지만 다룬다(같은 내용을 두 곳에 쓰지 않는다). 해당 없는 절은 "해당 없음 — 이유"로 남긴다(지우지 않는다: 빠뜨린 건지 판단한 건지 구분되게).
읽는 사람은 사용자(결정 확인용)와 하위 개발 세션(그대로 구현할 기준)이다. 모호한 표현 대신 이름·숫자·경로로 쓴다.

````markdown
# <제품명> 아키텍처

작성 <날짜> · 상태 <초안 | 확정 | 개정 n>

## 1. 목적과 사용자
- 기능 정의서: `docs/SPEC.md` (<상태·날짜>)
- 한 줄 소개: <무엇을 누구에게>
- 사용자 유형:

  | 유형 | 하는 일 | 권한 |
  |---|---|---|

- 꼭 지켜야 할 조건: <지정 서버·DB·포트·도메인, 기존 시스템 연동, 보안·과금 요구>

## 2. 범위
- SPEC 의 우선순위를 따른다: 이번 <기능 ID 범위>, 다음 <>, 나중 <>. 기술적으로 범위가 바뀌는 점만 여기 적는다.

## 3. 기존 시스템 분석 (있으면)
- 위치·구조 요약, 쓸 만한 것 / 버릴 것, 숨은 규칙(계산식·권한 예외·데이터 정리 규칙)

## 4. 전체 구조
```
<텍스트 구조도: 사용자 → 화면 → API 서버 → 저장소(들) / 외부 연동 / 배치>
```
- 요청 흐름 한 가지를 예로 따라가기: <로그인 → 조회 → 저장 시 거치는 계층>

## 5. 기술 선택
| 영역 | 선택 | 버전 | 이유 |
|---|---|---|---|
| 서버 | <> | <> | <> |
| 화면 | <> | <> | <> |
| 저장소 | <> | <> | <> |
| 배포 | <> | <> | <> |

## 6. 결정 기록
| # | 결정 | 이유 | 버린 대안 | 되돌리기 비용 |
|---|---|---|---|---|

## 7. 데이터 모델
- 저장소별로 나눈다(예: 관계형 = 계정·권한·과금, 문서형 = 사용자 정의 데이터).
- 테이블/컬렉션마다: 이름, 핵심 필드(타입·필수·고유), 인덱스, 관계, 누가 쓰고 읽는지.
- 다중 조직이면 모든 데이터에 조직 키가 있는지, 조직 간 참조가 생기지 않는지 명시.

## 8. 권한·보안
- 인증 방식, 세션/토큰 만료
- 역할 × 기능 표(누가 무엇을 할 수 있는지)
- 권한 검사 위치(서버 공통 가드 등), 조직 경계 검사
- 비밀 관리(.env 위치), 감사 로그 대상, 개인정보 처리

## 9. API 설계 원칙
- 경로 규칙, 입력 검증 방식, 오류 형식(사용자에게 보일 문구 언어), 페이징·정렬·검색 규칙, 파일 업로드 한도

## 10. 화면과 API·데이터 연결
화면의 목적·동작은 SPEC '화면 정의'. 여기에는 구현 연결만.

| 화면 (SPEC) | 경로 | 쓰는 API | 읽고 쓰는 데이터 | 권한 검사 |
|---|---|---|---|---|

- UI 라이브러리와 특수 부품(차트·표·에디터), 디자인 토큰(색·글꼴·간격·모서리)을 정의한 위치, 공통 레이아웃
- 반응형 기준 폭(예: 375 / 768 / 1440). 디자인 방향 자체는 SPEC '디자인 기준'을 따른다

## 11. 배포·운영
- 환경(로컬·운영), 배포 방법과 명령, 상태 확인 주소
- 설정 항목(.env 키 목록 — 값은 쓰지 않음)
- 로그 확인, 백업·복구, 재배포·되돌리기 방법

## 12. 성능·한도
- 예상 데이터 양, 느려질 수 있는 지점과 대책(인덱스, 페이징, 버퍼링)
- 요금제·사용량 한도가 있으면 측정 방법과 차단/과금 규칙

## 13. 테스트·검수 전략
- 자동 테스트 범위(핵심 계산·변환·권한), 브라우저 검수 범위
- 샘플 데이터(실제 업무와 비슷한 데이터, 경계 사례)

## 14. 위험과 미정 사항
| 항목 | 내용 | 정할 사람·시점 |
|---|---|---|

## 15. 작업 분할 (구축 단계 입력)
| 작업 | 기능 ID | 담당 범위(폴더·파일) | 먼저 끝나야 할 것 | 완료 기준 |
|---|---|---|---|---|

- SPEC 의 '이번' 기능 ID 가 모두 어느 작업엔가 들어갔는지 확인(빠진 ID 없음). 완료 기준은 SPEC 의 기능 완료 기준을 그대로 쓴다.

- 같은 파일을 두 작업이 동시에 고치지 않게 나눴는지 확인
- 첫 사이클 목표: <한 사용자가 처음부터 끝까지 쓸 수 있는 가장 작은 흐름>
````
