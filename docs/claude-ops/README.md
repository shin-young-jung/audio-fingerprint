# Claude 운용 전략 — 모델·세션을 어떻게 굴릴지 (범용)

이 폴더는 **Claude 를 어떻게 나눠 쓸지**만 담는다(어떤 모델로, 세션을 몇 개, 누가 검수). 무엇을 어떻게 만들지(설계·품질 기준)는 [../playbook/](../playbook/README.md) 에 있다.
모델이 바뀌거나 운용 방식을 바꾸면 이 폴더만 고친다. 어느 프로젝트에나 `docs/claude-ops/` 로 복사해 쓴다.

## 단계별 구성 (전략 1안)

| 단계 | 구성 | 모델 | 쓰는 프롬프트 |
|---|---|---|---|
| 설계 | 메인 세션 하나가 직접. 기존 코드 조사만 읽기 전용 하위 세션에 맡길 수 있다 | 메인 Opus·높음, 조사 Sonnet | [../playbook/ARCHITECTURE_PROMPT.md](../playbook/ARCHITECTURE_PROMPT.md) |
| 구축 (첫 사이클) | 메인 = 관리자(분할·지시·검증·커밋·배포), 하위 = 개발 세션 여러 개 + 검수 전용 세션 | 메인 Opus·높음, 하위 Sonnet·보통 | [MANAGER_PROMPT.md](MANAGER_PROMPT.md) |
| 유지보수 | 버그 묶음마다 새 세션 하나가 재현~배포까지 | Sonnet·보통 (막히면 Opus 로 바꿔 이어서) | [BUGFIX_PROMPT.md](BUGFIX_PROMPT.md) |

## 원칙
- **세션은 자기 모델을 못 바꾼다.** 새 대화를 열 때 모델을 먼저 고른다. 하위 세션은 만드는 쪽이 모델을 지정한다.
- **작업 단위마다 새 세션.** 긴 대화는 매 턴 비용이 커진다. 같은 작업의 재작업만 같은 세션에 보낸다.
- **만든 세션 ≠ 검수하는 세션.** 자기 결과를 자기가 검수하지 않는다.
- **쓰기 세션끼리 파일이 겹치지 않게.** 겹치면 순서대로.
- **커밋·배포는 한 곳에서.** 구축은 메인이, 유지보수는 그 세션이.
- **작은 수정은 직접.** 원인을 이미 찾았고 30줄 안쪽이면 다른 세션에 설명하지 않고 고친다.

## 관리자 구조가 손해인 경우
아래는 관리자 + 하위 세션 구조보다 **세션 하나**가 낫다.
- 작은 프로젝트, 화면 몇 개짜리 기능
- 원인을 모르는 버그(진단과 수정이 한 흐름이어야 함)
- 여러 파일에 얽힌 한 덩어리 변경(나누면 맞추는 비용이 더 큼)
- 이미 구축이 끝난 뒤의 자잘한 수정 묶음 → 유지보수 구성

## 쓰는 법 (새 대화에 그대로 입력)
- 설계: 모델 Opus·높음 → "`docs/playbook/ARCHITECTURE_PROMPT.md` 읽고 그대로 해. 요청: ○○"
- 설계부터 구축까지 한 번에: 위 문장 뒤에 "설계가 확정되면 `docs/claude-ops/MANAGER_PROMPT.md` 방식으로 1차 구축까지 진행해."
- 구축: 모델 Opus·높음 → "`docs/claude-ops/MANAGER_PROMPT.md` 읽고 그대로 해. 이번 작업은 ○○"
- 버그: 모델 Sonnet·보통 → "`docs/claude-ops/BUGFIX_PROMPT.md` 읽고 그대로 해. 버그 목록: 1. ○○ 2. ○○"
- 프로젝트 덧붙임 파일(`docs/MANAGER_PROMPT.md` 등)이 있으면 그것을 대신 가리킨다. 덧붙임은 "범용판을 따르고 이 프로젝트는 아래를 추가로 지킨다" + 배포 방법·사용자 성향 같은 고유 사항만 적는다.
